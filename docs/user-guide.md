# Руководство планировщика

Это руководство для планировщика программы и руководителя ОКР. Оно идёт по рабочему циклу: подготовить данные, собрать программу, найти конфликты, построить и сравнить варианты, оценить риск, поправить план вручную и принять решение, разобраться в причинах переносов, перепланировать после изменений. Справочные таблицы вынесены отдельно: [форматы данных](data-format.md) и [коды](reference-codes.md).

Все команды запускаются как `SynAPS-ProgramPlan <команда>`; из исходников — `python -m synaps_programplan <команда>`. Ответ печатается в формате JSON, планы и отчёты пишутся в файлы.

## 1. Установка и проверка

```text
pip install "SynAPS-ProgramPlan[api] @ git+https://github.com/KonkovDV/SynAPS-ProgramPlan.git"
SynAPS-ProgramPlan version
```

Дополнение `[api]` нужно для рабочего места (`serve`) и HTTP-контура; для расчётов из командной строки достаточно пакета без него.

`version` показывает версию, зафиксированный коммит ядра SynAPS, уровень зрелости и уровень утверждений. Эти же поля попадают в доказательную базу каждого плана.

Чтобы увидеть всё сразу на учебной программе, соберите показ и откройте оба отчёта в браузере. Другой лимит времени даст другой план, поэтому для показа держат файлы этой команды. Порядок экрана — в [сценарии показа](acceptance/demo-script.md).

```text
SynAPS-ProgramPlan demo --projects 4 --time-limit 8 --risk-runs 40 --out-dir out/demo
```

## 2. Подготовка данных

### Единицы, которые нужно знать

- **Время** — рабочие дни. Длительности, лаги, лимиты сдвига задаются в рабочих днях (`_wd` в названии колонки). Календарь — производственный календарь РФ: 2025–2027 годы по постановлениям Правительства, следующие — по правилу ст. 112 ТК РФ с пометкой «предварительно».
- **Люди** — в десятых долях ставки: `10` = 1 ставка, `5` = 0,5 ставки. Группа из трёх человек одной специальности — ресурс с ёмкостью `30`.
- **Стенды и оборудование** — в штуках: стенд — обычно ёмкость `1`.
- **Сроки двух видов.** Директивный срок (`deadline`, `latest_finish`) — жёсткий: план, который его нарушает, не публикуется. Плановый срок (`due_date`) — мягкий: его нарушение допускается, но считается просрочкой и минимизируется.

### Вариант А: из MS Project

Каждый проект ОКР — отдельный файл MS Project, сохранённый как XML (*Файл → Сохранить как → XML*). Межпроектные связи задаются отдельной таблицей CSV, потому что файлы MS Project не умеют надёжно ссылаться на работы друг друга:

```text
src_project,src_uid,dst_project,dst_uid,type,lag_wd
okr1,12,okr2,5,FS,0
okr2,30,okr3,7,SS,3
```

`src_uid` и `dst_uid` — уникальные номера работ (UID) в MS Project. Разделитель — запятая, точка с запятой или табуляция.

Файл MPP или MPX читается той же командой `import`. Для этого нужны Java 17 и дополнительный пакет: `pip install "SynAPS-ProgramPlan[mpp]"`. Разбор бинарного MPP делает библиотека MPXJ; сопоставление полей такое же, как у XML, и всё пропущенное попадает в тот же отчёт импорта.

### Вариант Б: из Primavera P6

Выгрузите проекты программы в один файл XER (*File → Export → Primavera PM (XER)*). Один файл может содержать несколько проектов: каждый станет отдельной ОКР с кодом из поля «Project ID» (`proj_short_name`), а связи между работами разных проектов Primavera хранит сама — отдельная таблица CSV не нужна. Сопоставление полей — в [форматах данных](data-format.md#primavera-p6-xer).

### Вариант В: из Excel

```text
SynAPS-ProgramPlan template --out program.xlsx
```

Шаблон содержит десять листов — `Program`, `Projects`, `WBS`, `Tasks`, `Demands`, `Dependencies`, `Resources`, `Skills`, `Exceptions`, `Risks` — с заголовками и строкой-примером, начинающейся с `#` (такие строки не читаются). Достаточно заполнить `Program`, `Projects`, `Tasks`; остальное — по мере наличия данных. Лист `Risks` — реестр драйверов риска (раздел 10). Состав колонок и значения по умолчанию — в [форматах данных](data-format.md#книга-excel). Книга, которая при распаковке раздувается сильнее обычной, не читается.

Перед передачей файла заказчик может заменить имена кодами и сдвинуть даты на постоянное число дней, не трогая структуру:

```text
python scripts/anonymize_program.py program.json --shift-days 100 --out anonymized.json
```

Скрипт запускается у заказчика. Соответствие кодов именам не сохраняется, а `anonymized.json` в репозиторий не кладётся.

### Что проверить в данных до расчёта

- У каждой работы есть хотя бы одна связь, а каждая цепочка ведёт к вехе.
- Ресурсы названы одинаково во всех файлах: «Стенд ТС-1» и «стенд  тс-1» считаются одним ресурсом (регистр, лишние пробелы и «ё/е» не важны), «ТС-1» и «Стенд ТС-1» — разными.
- Директивными отмечены только сроки, которые действительно нельзя сдвигать. Если жёстких дат больше 5% работ, анализ выдаст предупреждение `HARD_CONSTRAINTS`.

## 3. Сборка программы

```text
SynAPS-ProgramPlan import okr1.xml okr2.xml okr3.xml --codes okr1 okr2 okr3 --links links.csv --status-date 2027-01-11 --name "Программа ОКР" --provenance customer_anonymized --out program.json
```

из Primavera:

```text
SynAPS-ProgramPlan import portfolio.xer --provenance customer_anonymized --out program.json
```

или из Excel:

```text
SynAPS-ProgramPlan import program.xlsx --provenance customer_anonymized --out program.json
```

Файлы MS Project (XML, MPP, MPX) и XER можно смешивать в одной команде. Если два проекта получили один код ОКР, импорт остановится с ошибкой: задайте `--codes` для файлов MS Project или переименуйте проект в источнике.

Ответ показывает число работ, общие ресурсы (`shared_resources`) и расхождения ёмкости одноимённого ресурса в разных файлах (`capacity_conflicts`, берётся максимум). В `notes` и в `losses` перечислено всё, что импорт приблизил или пропустил: ограничения ALAP, SNLT и FNET, календарные лаги, связи от суммарных задач, материальные ресурсы, работы уровня усилий Primavera. Запись `--losses losses.json` сохраняет тот же список кодами. `--strict` не записывает программу и возвращает код 2, если в файле есть пропуск, приближение или урезание. Сообщение, что базовый план Primavera в XER лежит отдельным проектом, импорт не блокирует: в этом файле его нет. Ничего не отбрасывается молча.

Если один стенд в файлах назван по-разному, передайте таблицу `import a.xml b.xml --aliases names.csv` с колонками `alias` и `canonical`. Без этой строки похожие имена только перечисляются в отчёте и остаются разными ресурсами.

Ключ `--soft-deadlines` превращает поле Deadline из MS Project в плановый (мягкий) срок вместо директивного. `--provenance` записывает происхождение данных; для данных заказчика используйте `customer_anonymized` (см. [данные и безопасность](security-and-data.md)).

## 4. Конфликты до оптимизации

```text
SynAPS-ProgramPlan analyze program.json
```

Анализ работает по исходным датам, как они пришли из планов ОКР, и отвечает на вопрос «где программа не сходится уже сейчас»:

- `OVERLOAD` — ресурс перегружен в исходных планах;
- `SHARED_CONTENTION` — перегрузка возникает из-за двух и более ОКР на одном ресурсе;
- `SKILL_POOL_OVERLOAD` — не хватает людей нужной компетенции;
- `LINK_BROKEN` — исходные даты нарушают связь (обычно после добавления межпроектных связей);
- `DEADLINE_IMPOSSIBLE` — срок недостижим даже при неограниченных ресурсах;
- `DEADLINE_AT_RISK` — резерв времени мал, а выше по цепочке есть перегрузки;
- `DEADLINE_MISSED_IN_SOURCE` — исходный план уже нарушает срок.

Там же выдаётся оценка качества данных (`quality`): работы без связей, без ресурсов, слишком длинные, отрицательные лаги, работы, которые должны были начаться до даты статуса, даты на выходных. Полный список — в [справочнике кодов](reference-codes.md#конфликты-исходных-планов).

## 5. Построение плана и вариантов

Один план:

```text
SynAPS-ProgramPlan solve program.json --out plan.json --explain
```

Все варианты сразу:

```text
SynAPS-ProgramPlan scenarios program.json --out-dir out --explain
```

| Вариант | Что оптимизирует | Когда смотреть |
|---|---|---|
| **A · Сроки** | Сначала суммарную просрочку, затем окончание каждой ОКР | Базовый ответ «как быстрее всего» |
| **B · Ресурсы** | То же, но общие ресурсы загружены не больше чем на 80% (если невыполнимо — на 90%) | Нужен запас на непредвиденное |
| **C · Стабильность** | Минимальные отклонения от утверждённого плана; ничего не начинается раньше утверждённого | Важно не ломать договорённости с исполнителями |
| **D · Баланс** | Окончание программы не позже A более чем на 5%, при этом минимум отклонений | Компромисс между сроком и стабильностью |
| **P · Приоритет** | Сначала ОКР с более высоким приоритетом: их вехи и окончания закрепляются, затем планируется следующий уровень | Приоритеты ОКР заданы и срок важной ОКР нельзя отдавать менее важной. Строится, только если приоритетов больше одного |
| **E · Что если** | Вариант A на изменённой программе | Оценить решение до его принятия |
| **R · Правка** | Ручные правки планировщика закреплены, остальное перестроено (раздел 12) | Планировщик знает то, чего нет в данных |

Если два варианта дали одинаковые даты, второй помечается как совпадающий (`duplicate_of`) и не дублируется в отчёте. Если вариант невыполним (типично для B, когда стенд в единственном экземпляре), он остаётся в таблице сравнения с вердиктом `INFEASIBLE`, но в Гант не попадает.

Сценарии «что если» описываются файлом JSON (формат — в [форматах данных](data-format.md#сценарии-что-если)):

```text
SynAPS-ProgramPlan scenarios program.json --out-dir out --what-if whatif.json
```

Полезные параметры `solve`, `scenarios`, `repair`, `replan`, `serve`:

| Параметр | Значение |
|---|---|
| `--time-limit 20` | Секунд на один расчёт. Больше — выше шанс `OPTIMAL` на крупной программе. |
| `--objective finish` | Цель: `finish` — раньше закончить каждую ОКР; `due` — меньше просрочка плановых сроков; `stability` — меньше отклонений от утверждённого плана. |
| `--solver cpsat` | `cpsat` — точный решатель; `greedy` — быстрый жадный план, невыполнимость не доказывает. |
| `--seed 42` | Начальное число генератора. С тем же числом на тех же данных получается тот же план (сверяется по `plan_hash`). |

## 6. Как читать отчёт

```text
SynAPS-ProgramPlan report program.json out/plan_A.json out/plan_C.json out/plan_D.json --risk-runs 200 --out report.html
```

Файл открывается в любом браузере без сети. Разделы сверху вниз:

1. **Предупреждения** — предварительный календарь, происхождение данных, свидетель невыполнимости.
2. **Сравнение вариантов** — окончание программы, просроченные вехи, суммарная просрочка, число и сумма сдвигов, пиковая загрузка. Лучшее значение в колонке выделено. Вариант «что если», который меняет программу (другая ёмкость, снятая ОКР), остаётся в этой таблице. На диаграмму исходной программы его полосы не наносятся: у пункта списка пометка «только в таблице». Даты такого варианта относятся к изменённой программе, и хеш входа с исходной программой не совпадает.
3. **Показатели варианта** — карточки основных показателей и окончание каждой ОКР.
4. **Диаграмма Ганта** — масштаб (вся программа, недели, месяцы, кварталы), фильтр по ОКР, предприятию и ресурсу, «только критические», «только сдвинутые», исходный план серым, связи, поиск. Заголовок ОКР или этапа сворачивает ветку. У вехи с оценкой P80 зелёная точка значит «P80 не позже срока», красная — «P80 позже срока». Режим правки — раздел 12. Подсказка на полосе показывает причину переноса.
5. **Риск срыва сроков** (если задан `--risk-runs`) — P50/P80/P90, драйверы риска, вехи, индекс критичности (раздел 10).
6. **Загрузка ресурсов** — тепловая карта пиковой загрузки по месяцам; щелчок по строке открывает дневной профиль с линией доступности.
7. **Почему работы перенесены** — причина, цепочка до первопричины, а для крупнейших сдвигов — «если оставить на месте».
8. **Конфликты исходных планов** — то, что нашёл `analyze`.
9. **Нарушения и предупреждения** — предупреждения принятого варианта (жёстких нарушений у принятого плана нет по определению).
10. **Доказательная база** — версии, коммит ядра, хеш входа, настройки, хеш плана.

Раздел риска строится по варианту `--risk-scenario` (по умолчанию — первому принятому); `--seed` задаёт выборку.

## 7. Почему работа перенесена

```text
SynAPS-ProgramPlan explain program.json plan.json --counterfactuals 3
```

Для каждой сдвинутой работы и каждой просроченной вехи определяется ограничение, которое держит её начало в итоговом плане:

- **связь** — работа ждёт предшественника, в том числе из другой ОКР (`CROSS_PROJECT_DEPENDENCY`);
- **ресурс** — нужный человек или стенд в предыдущий день занят другими работами; названы эти работы и их ОКР (`RESOURCE_CONTENTION`);
- **календарь ресурса** — отпуск или ремонт (`CALENDAR_CLOSURE`);
- **окно** — дата статуса, «не раньше», лимит сдвига, закрепление, заморозка, ограничение варианта или ручная правка;
- **выбор оптимизатора** — ни одно ограничение не активно, дата выбрана ради общей цели (`OPTIMIZER_CHOICE`).

Если причина — связь, система идёт по цепочке назад до первопричины: «сдвинута, потому что ждёт Б, которая ждёт В, а В ждёт стенд ТС-1, занятый ОКР-3».

С ключом `--counterfactuals N` для N крупнейших сдвигов выполняется пересчёт «а если оставить эту работу на утверждённых датах»: насколько тогда сдвинется окончание программы, или что это невозможно.

Записка языковой модели строится отдельно и только по уже принятому плану:

```text
SynAPS-ProgramPlan ask program.json plan.json --question "Почему сдвинуты испытания опытного экземпляра?"
```

Без `SYNAPS_PROGRAMPLAN_YANDEX_API_KEY` и `SYNAPS_PROGRAMPLAN_YANDEX_FOLDER` команда отвечает, что модель выключена, и в сеть не обращается. Когда обе переменные заданы, в Yandex Cloud AI Studio уходят факты принятого плана, не файл заказчика целиком. Фраза без ссылки на такой факт в ответ не попадает. Модель план не меняет. Имя модели по умолчанию `yandexgpt`; другое имя задаёт `SYNAPS_PROGRAMPLAN_YANDEX_MODEL`. Адрес сервиса — `https://ai.api.cloud.yandex.net/v1/chat/completions`, модель указывается как `gpt://<каталог>/<имя>/latest`. Ключ — API-ключ сервисного аккаунта с областью `yc.ai.languageModels.execute`.

## 8. Если программа невыполнима

```text
SynAPS-ProgramPlan witness program.json
```

Свидетель невыполнимости — набор требований (директивные сроки, закрепления, заморозка, лимиты сдвига, «не раньше», ограничения ресурсов, максимальные лаги), которые вместе выполнить нельзя. Набор ищется последовательным удалением лишнего. Поле `minimal = true` значит, что в пределах числа проверок каждое оставшееся требование необходимо. Для директивного срока отдельно считается, хватает ли снять его одного: тогда в записи стоит `alone_sufficient` и подсказка, на какую дату срок перенести (`suggestion`). Пример ответа:

```text
несовместимы требования: директивный срок «Веха: Корректировка РКД и приёмка — завершение» 20.08.2027
```

Если требований несколько и для выполнимости хватает снять любое одно, ответ заканчивается фразой «Достаточно ослабить любое из них». Если одного мало, ответ говорит, что ослабить нужно весь набор. При одном требовании этих фраз нет: на экране сам срок.

Если программа невыполнима даже без всех ослабляемых требований, свидетель так и скажет: проблема в самих длительностях, связях или ёмкости ресурсов.

## 9. Перепланирование на новую дату статуса

Когда наступила новая дата статуса, работы выполнены или задержаны, а ресурс выбыл:

```text
SynAPS-ProgramPlan repair program.json plan.json --status-date 2027-03-01 --freeze-wd 10 --delay okr2.17=5 --unavailable stand-1:2027-03-10:2027-03-24 --out plan2.json --out-program program2.json
```

- работы, закончившиеся по плану до даты статуса, считаются выполненными, а начатые — выполняемыми;
- прежний план становится утверждённой базой для сравнения;
- работы, которые начинаются в ближайшие `--freeze-wd` рабочих дней, не двигаются;
- `--delay работа=+дни` удлиняет работу; `--unavailable ресурс:с:по` закрывает ресурс на период (оба ключа можно повторять).

`program2.json` — обновлённая программа для следующего цикла, `plan2.json` — новый план с объяснениями.

## 10. Риск срыва

```text
SynAPS-ProgramPlan risk program.json plan.json --runs 200 --seed 42 --out risk.json
```

Работает только по принятому плану. В каждой выборке:

1. длительность каждой ещё не начатой работы случайно меняется от 80% до 150% плановой (треугольное распределение с модой в плановом значении);
2. каждый **драйвер риска** из реестра «срабатывает» со своей вероятностью и, если сработал, умножает длительности своих работ на случайный множитель из диапазона «минимум — наиболее вероятно — максимум»;
3. программа пересобирается в порядке принятого плана с теми же назначенными людьми и стендами, с учётом связей, их лагов и ранних дат.

Драйвер риска — именованный риск с владельцем, например «повторные испытания после отказа на стенде» с вероятностью 35% и множителем 1,1–1,4–1,9 для работ этапа предварительных испытаний. Реестр задаётся листом `Risks` книги Excel или полем `risk_drivers` программы ([форматы данных](data-format.md#risks--реестр-драйверов-риска)).

Результат:

- `program_finish` — даты P50, P80, P90 окончания программы;
- `deadlines_met_share` — доля выборок, в которых соблюдены все директивные сроки;
- `milestone_risk` — для каждой вехи P50/P80/P90, её срок и `on_time_share` — доля выборок, в которых веха уложилась в срок;
- `drivers` — для каждого драйвера: как часто он сработал и на сколько рабочих дней раньше стал бы P80 окончания программы, если бы этого риска не было (`p80_gain_wd`). Драйверы отсортированы по этому выигрышу: сверху — риски, с которых выгоднее всего начинать меры;
- `criticality` — индекс критичности: доля выборок, в которых у работы нулевой резерв по методу критического пути (без учёта ресурсов); `--brief` убирает его из ответа;
- `scheduled_runs` — сколько выборок поместилось в горизонт программы; не поместившиеся считаются несоблюдением сроков, и об этом написано в `note`.

Как читать. Если P80 вехи позже её срока, а `on_time_share` ниже 0,8, срок под угрозой. Если наверху списка драйверов стоит «повторные испытания» с выигрышем 22 р.д., то мера против этого риска (резервный стенд, предварительный прогон) даст больше, чем меры против остальных. Без разброса и драйверов выборка воспроизводит принятый план день в день — это проверено тестом.

Это частоты выборки на уже принятом плане: см. [методологию](methodology.md#10-оценка-риска).

## 11. Рабочее место планировщика

```text
SynAPS-ProgramPlan serve program.json out/plan_A.json out/plan_D.json --journal decisions.jsonl --risk-runs 200 --time-limit 10
```

Откройте `http://127.0.0.1:8765/`. Это тот же отчёт, что в разделе 6, но подключённый к серверу:

- правки проверяет сервер той же независимой проверкой, что оптимизированный план;
- кнопка «пересчитать план с правками» строит новый вариант R1, R2, … и добавляет его в сравнение;
- раздел «Решение по варианту» записывает принятие или отклонение с обоснованием в журнал;
- кнопки «план (JSON)» и «план для MS Project (XML)» выгружают выбранный принятый вариант.

Параметры: `--host` и `--port` — адрес; `--journal` — файл журнала решений; `--save-dir` — куда сохранять варианты R (по умолчанию — каталог журнала); `--witness` — файл свидетеля невыполнимости для отчёта; `--risk-runs` — раздел риска; `--tls-cert` и `--tls-key` — сертификат и ключ TLS; параметры расчёта — как в разделе 5.

**Роли.** Без настройки рабочее место работает в локальном режиме: один пользователь `local` с ролью планировщика, ответы только на локальном адресе (`127.0.0.1`, `localhost`); запуск на другом адресе будет отклонён. Для нескольких пользователей администратор задаёт переменную окружения `SYNAPS_PROGRAMPLAN_TOKENS` до запуска (формат — в [данных и безопасности](security-and-data.md#4-роли-и-доступ-к-рабочему-месту)). Браузер спросит токен при первом обращении и будет хранить его до закрытия вкладки. Адрес не из локальных принимается только вместе с ролями и TLS: сам сервер не слушает сеть без сертификата. Корпоративный вход делается на прокси перед локальным адресом; прокси передаёт пользователя заголовками `X-Remote-User` и `X-Remote-Role` и секретом `X-Synaps-Proxy-Secret`.

| Роль | Смотреть и проверять правки | Принимать и отклонять варианты | Пересчитывать план с правками |
|---|---|---|---|
| Планировщик программы (`planner`) | да | да | да |
| Руководитель ОКР или программы (`manager`) | да | да | нет |
| Наблюдатель (`observer`) | да | нет | нет |

**Перезапуск.** Варианты R сохраняются как `plan_R1.json`, `plan_R2.json` … рядом с журналом. При следующем запуске с тем же журналом они подгружаются сами, если журнал цел, хеш плана совпадает с записанным в журнале, программа та же и независимая проверка чиста. Нумерация продолжается: новый вариант не перезапишет уже принятый.

## 12. Ручная правка плана

Включите **режим правки** над диаграммой Ганта.

- **Мышью:** перетащите полосу работы или ромб вехи. Шаг — рабочий день, выходные и праздники пропускаются.
- **Клавиатурой:** выберите работу щелчком или клавишей Tab и сдвигайте стрелками ← → на один рабочий день, с Shift — на пять. Esc снимает выбор.
- Начатые и выполненные работы не двигаются.
- Исправленная работа обведена, отмечена «✎», а её прежнее положение показано пунктиром.
- «Отменить шаг» и «сбросить правки» возвращают план; «скачать правки (JSON)» сохраняет файл правок.

**Мгновенная проверка.** После каждой правки под панелью появляется результат: число жёстких нарушений, сравнение показателей «вариант / с правками» (окончание программы, просроченные вехи, суммарная просрочка, сдвиги, пиковая загрузка) и список нарушений с кодами — например `PRECEDENCE_FS_BROKEN` (работа начата раньше окончания предшественника), `CAPACITY_EXCEEDED` (стенд занят), `DEADLINE_MISSED`.

**Пересчёт с правками.** Правка редко бывает допустимой сама по себе: если работа сдвинута позже, её последователи должны сдвинуться тоже. Кнопка «пересчитать план с правками» закрепляет правки на выбранных датах и перестраивает остальное. Режимы:

- **минимум перестановок** (по умолчанию) — ни одна другая работа не ставится раньше, чем в исходном варианте, и минимизируется суммарное запаздывание относительно него. После пересчёта сдвиги разделены: закреплённая правка, работы по связям за ней, работы на тех же ресурсах и компетенциях, и работы без связи с правкой. Порог пилота «меньше 10%» относится только к последней группе: задержка в начале цепочки обязана сдвинуть всё, что за ней идёт. На учебной программе из 96 работ сдвиг `okr1.TZ.1` на 5 рабочих дней переставил 77 работ: 50 по связям, 26 на общих ресурсах, 0 без связи с правкой;
- **переоптимизировать сроки** — остальная программа решается заново по цели расчёта; окончание может стать лучше, но меняется больше работ (на том же примере — 73 из 96).

Если с минимумом перестановок правку выполнить нельзя, система сама переходит к переоптимизации и сообщает об этом. Новый вариант публикуется, только если прошёл обе проверки; иначе показывается причина отказа, и правки остаются на экране для исправления.

**Без сервера.** В статическом отчёте режим правки тоже работает, но проверка там **предварительная**: браузер проверяет связи, максимальные лаги, сроки и загрузку поимённых ресурсов с учётом их отпусков и ремонтов, а пулы компетенций, лимиты сдвига, закрепления и заморозку — нет. Окончательный ответ даёт команда:

```text
SynAPS-ProgramPlan check program.json plan_A.json --moves edits_A.json
SynAPS-ProgramPlan replan program.json plan_A.json --moves edits_A.json --mode stable --scenario-id R1 --out plan_R1.json
```

`check` печатает нарушения и показатели с правками (код выхода 1 при жёстком нарушении); `replan` строит вариант с закреплёнными правками (`--mode optimise` — переоптимизировать сроки).

## 13. Решения и журнал

В рабочем месте выберите вариант, укажите обоснование (обязательно, от 3 символов) и нажмите «принять вариант» или «отклонить вариант». Принять можно только вариант, прошедший проверку, и только когда на нём нет несохранённых правок. Пересчёт с правками записывается в журнал автоматически.

Каждая запись журнала хранит время (UTC), пользователя и роль, действие, вариант, хеш плана, хеш входной программы, обоснование и подробности (например, какие работы куда сдвинуты). Записи связаны хеш-цепочкой: изменение, удаление или перестановка любой записи внутри журнала обнаруживается. В рабочем месте целостность показана над таблицей журнала; из командной строки:

```text
SynAPS-ProgramPlan journal decisions.jsonl --tail 5
```

Код выхода 1 — журнал нарушен: номер испорченной записи в `broken_at`, а если обрезан хвост или файл заменён целиком — причина в `reason`. Рядом с журналом лежит печать `decisions.jsonl.head` (число записей и хеш последней). Поле `head` в ответе — этот хеш: его стоит скопировать в протокол совещания и потом проверять так:

```text
SynAPS-ProgramPlan journal decisions.jsonl --anchor <хеш из протокола>
```

Подмена и журнала, и печати одновременно этой командой без `--anchor` не видна. `--seal` записывает печать для уже существующего журнала и отказывается, если печать уже есть и не сходится с файлом. Если администратор задал `SYNAPS_PROGRAMPLAN_JOURNAL_KEY`, каждая новая запись подписывается, а `journal --key` с другим ключом журнал не принимает. Подробности — в [данных и безопасности](security-and-data.md#5-журнал-решений).

## 14. Возврат плана в MS Project

```text
SynAPS-ProgramPlan export program.json plan.json --out plan.xml
```

Выгружается только принятый план. Структура: ОКР, внутри пакеты работ, внутри работы. В файл попадают даты, связи с задержками, трудовые ресурсы и назначения, директивные сроки, а в примечании к работе — хеш плана и причина переноса. Базовый план 0 — даты, с которыми этот план сравнивался. Работы записаны как планируемые вручную, поэтому MS Project показывает ровно проверенные даты и не переставляет их своим выравниванием.

## 15. Независимая проверка любого плана

```text
SynAPS-ProgramPlan check program.json plan.json
```

Проверка читает только программу и даты плана и не использует решатель. Её можно применить и к плану, отредактированному вручную в файле: она покажет каждое нарушение с кодом (см. [справочник](reference-codes.md#нарушения-независимой-проверки)).

## 16. Частые вопросы

**Вариант B всегда `INFEASIBLE`. Это ошибка?** Нет. Резерв ёмкости у стенда в единственном экземпляре означает «стенд недоступен», и работы на нём выполнить нельзя. Результат верный: запаса по такому стенду нет.

**Вердикт `ERROR`, а не `INFEASIBLE`. Что делать?** Невыполнимость не доказана — скорее всего, не хватило времени. Увеличьте `--time-limit` или запустите `witness`.

**Варианты C и A совпали.** При сильной перегрузке общих ресурсов ресурсы и связи оставляют мало свободы: самый быстрый план оказывается и самым близким к утверждённому. Таблица сравнения покажет это как `duplicate_of`.

**В «что если» со вторым стендом окончание программы стало позже.** Цель варианта — сначала суммарная просрочка вех и только затем окончание. Сравнивайте колонку «Просрочка, р.д.»; и проверьте вердикт: `FEASIBLE` означает, что лучший план мог не найтись за лимит времени.

**P50 окончания программы позже, чем в плане.** Так и должно быть: среднее треугольного распределения 80–100–150% — около 110% плановой длительности, а драйверы риска только удлиняют работы. Плановые длительности — оптимистичная оценка; P80 показывает, какой срок реалистично обещать.

**Правка показала нарушение, но я уверен, что так можно.** Нарушение означает, что правка противоречит данным: связи, сроку или ёмкости. Либо пересчитайте план с правкой — система подвинет то, что мешает, — либо исправьте данные (связь, ёмкость, срок) и перестройте варианты.

**Браузер просит токен.** Рабочее место запущено с ролями. Токен выдаёт администратор контура; он хранится только во вкладке и не сохраняется после её закрытия.

**Плановые даты в MS Project стоят на выходных.** Анализ отметит их `NONWORKING_DATE`; при расчёте работы встают только на рабочие дни.

**Коды выхода.** `0` — план принят или проверка чиста; `1` — принятого плана нет, найдено жёсткое нарушение или журнал нарушен; `2` — ошибка во входных данных (текст ошибки — в stderr).
