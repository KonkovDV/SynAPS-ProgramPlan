# Форматы данных

Справочник по всем входам и выходам SynAPS-ProgramPlan: книга Excel, MS Project XML, MPP и MPX, Primavera P6 XER, таблица межпроектных связей, сценарии «что если», реестр рисков, файлы программы, плана, правок, риска и журнала решений. Как этими форматами пользоваться — в [руководстве планировщика](user-guide.md).

## Общие правила

| Правило | Значение |
|---|---|
| Даты | ISO `ГГГГ-ММ-ДД` или дата Excel |
| Время | рабочие дни (`_wd`), по календарю программы |
| Люди | десятые доли ставки: `10` = 1 ставка, `5` = 0,5 ставки |
| Стенды, лаборатории, оборудование | штуки: `1` = один стенд |
| Директивный срок | `deadline`, `latest_finish` — жёсткие: план с нарушением не публикуется |
| Плановый срок | `due_date` — мягкий: нарушение допускается и минимизируется как просрочка |
| Календарь | производственный календарь РФ; 2025–2027 годы — по постановлениям Правительства РФ (№1335, №1466, №1187, по 247 рабочих дней), следующие — по ст. 112 ТК РФ с пометкой «предварительно» |

## Книга Excel

Шаблон создаёт `SynAPS-ProgramPlan template --out program.xlsx`. Первая строка листа — заголовки; строки с пустой первой ячейкой или первой ячейкой, начинающейся с `#`, пропускаются. Несколько компетенций в одной ячейке разделяются `;`. Логические поля принимают `1`, `true`, `yes`, `да`.

Обозначения: **обяз.** — колонку нужно заполнить; пусто — подставляется значение по умолчанию.

### Program — программа (одна строка)

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор программы |
| `name` | обяз. | Название |
| `horizon_start` | обяз. | Начало горизонта планирования |
| `horizon_end` | обяз. | Конец горизонта (позже начала) |
| `status_date` | | Дата статуса: ничего нового не начинается раньше неё. Пусто — начало горизонта |

### Projects — проекты ОКР

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор ОКР |
| `code` | | Короткий код (по умолчанию `id`) |
| `name` | обяз. | Название |
| `priority` | | Приоритет 1–1000 (по умолчанию 500) |
| `due_date` | | Плановый срок окончания ОКР |
| `deadline` | | Директивный срок окончания ОКР |
| `enterprise` | | Предприятие-исполнитель. Сроки и загрузка стендов сводятся по этому имени |

### WBS — структура работ

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор узла |
| `project_id` | обяз. | ОКР |
| `parent_id` | | Родительский узел |
| `code` | | Код (по умолчанию `id`) |
| `name` | обяз. | Название |
| `kind` | | `STAGE` — этап, `PHASE` — фаза, `PACKAGE` — пакет работ (по умолчанию) |

### Tasks — работы и вехи

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор работы, уникальный в программе |
| `project_id` | обяз. | ОКР |
| `wbs_id` | | Узел структуры работ |
| `name` | обяз. | Название |
| `duration_wd` | | Длительность в рабочих днях. `0` или пусто — веха |
| `kind` | | `WORK` (по умолчанию), `MILESTONE` (по умолчанию при длительности 0), `TEST`, `REVIEW` |
| `status` | | `PLANNED` (по умолчанию), `IN_PROGRESS`, `DONE` |
| `earliest_start` | | Не раньше этой даты |
| `latest_finish` | | Не позже этой даты (жёстко) |
| `due_date` | | Плановый срок (мягко) |
| `deadline` | | Директивный срок (жёстко) |
| `shift_limit_wd` | | На сколько рабочих дней работу можно сдвинуть относительно утверждённого плана |
| `pinned` | | Закрепить на утверждённых датах |
| `remaining_wd` | | Остаток для выполняемой работы |
| `percent_complete` | | Процент выполнения, 0–100. У выполненной работы 100, у неначатой 0 или пусто, у начатой меньше 100 |
| `actual_start` | | Фактическое начало (нужно для `IN_PROGRESS` и `DONE`) |
| `actual_finish` | | Фактическое окончание (нужно для `DONE`) |
| `planned_start`, `planned_finish` | | Даты исходного плана ОКР: от них считаются сдвиги и конфликты |
| `okr_stage` | | Код этапа из справочника `src/synaps_programplan/okr_stages.json` (ТЗ, ЭП, ТП, РКД, изготовление опытного образца, предварительные испытания, государственные и сертификационные испытания). Справочник правится файлом, не кодом |
| `product_id` | | Изделие этой ОКР |
| `configuration_id` | | Конфигурация изделия |
| `test_article_id` | | Опытный экземпляр. Работа обязана занимать его ресурс |

Веха не может требовать ресурсов. Утверждённые даты, от которых считаются сдвиги, берутся в таком порядке: `baseline` программы, затем базовый план работы (`baseline_start`/`baseline_finish` из MS Project), затем `planned_start`/`planned_finish`.

Листы `Products` (`id`, `project_id`, `code`, `name`), `Configurations` (`id`, `product_id`, `code`, `name`) и `Articles` (`id`, `configuration_id`, `code`, `name`, `resource_id`) необязательны. Пустая книга без них открывается как раньше. Ресурс опытного экземпляра имеет ёмкость 1: два испытания одного экземпляра не встают на одни и те же дни, это проверяет обычная проверка ресурса.

### Demands — потребности работ в ресурсах

| Колонка | | Смысл |
|---|---|---|
| `task_id` | обяз. | Работа |
| `resource_id` | одно из двух | Конкретный человек, группа или стенд |
| `skill_id` | одно из двух | Компетенция: подойдёт любой человек с ней |
| `units` | | Сколько нужно (по умолчанию `1`). **Для людей это 0,1 ставки — для полной ставки укажите `10`** |

### Dependencies — связи

| Колонка | | Смысл |
|---|---|---|
| `src_task_id` | обяз. | Предшественник |
| `dst_task_id` | обяз. | Последователь |
| `type` | | `FS` — окончание→начало (по умолчанию), `SS` — начало→начало, `FF` — окончание→окончание, `SF` — начало→окончание |
| `lag_wd` | | Задержка в рабочих днях; отрицательная — опережение (по умолчанию 0) |
| `max_lag_wd` | | Максимальная задержка: последователь должен начаться (закончиться) не позже |
| `hard` | | Жёсткая связь (по умолчанию да); мягкая проверяется как предупреждение |
| `source` | | `IMPORTED` (по умолчанию), `MANUAL`, `CROSS_PROJECT` |

### Resources — ресурсы

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор |
| `kind` | обяз. | `PERSON`, `GROUP`, `STAND`, `LAB`, `EQUIPMENT`, `SOFTWARE` |
| `code` | | Код (по умолчанию `id`) |
| `name` | обяз. | Название |
| `capacity_units` | | Ёмкость (по умолчанию 1). Человек — `10`, группа из трёх — `30`, стенд — `1` |
| `skills` | | Компетенции через `;` |
| `org_unit` | | Подразделение |

### Skills — компетенции

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор |
| `code` | | Код (по умолчанию `id`) |
| `name` | обяз. | Название |

### Exceptions — отпуска, ремонты, внешние брони

| Колонка | | Смысл |
|---|---|---|
| `resource_id` | обяз. | Ресурс |
| `start`, `end` | обяз. | Период включительно |
| `units_available` | | Сколько остаётся доступно (по умолчанию 0 — ресурс закрыт) |
| `reason` | | `VACATION`, `MAINTENANCE`, `BOOKED_EXTERNAL`, `OTHER` (по умолчанию) |

### Risks — реестр драйверов риска

Необязательный лист. Драйвер риска — именованный риск, который с некоторой вероятностью удлиняет группу работ (подход AACE 57R-09). Используется только оценкой риска и не влияет на план.

| Колонка | | Смысл |
|---|---|---|
| `id` | обяз. | Идентификатор риска, уникальный |
| `name` | обяз. | Формулировка риска: «Повторные испытания после отказа на стенде» |
| `probability` | обяз. | Вероятность, что риск случится: больше 0 и не больше 1 (`0,35` или `0.35`) |
| `low`, `mode`, `high` | | Множитель длительности затронутых работ, если риск случился: минимум, наиболее вероятный, максимум; `low ≤ mode ≤ high`. По умолчанию `1,0`, `1,2`, `1,5` |
| `task_ids` | обяз. | Затронутые работы через `;` |
| `owner` | | Владелец риска |
| `group` | | Группа корреляции. Драйверы с одним именем группы используют одно случайное число на факт наступления: менее вероятный не случается без более вероятного. Пусто — риск независим |

Ссылка на несуществующую работу или повтор идентификатора отклоняются при чтении. Если сценарий «что если» исключает ОКР, её работы убираются из драйверов, а драйвер без работ — из реестра.

### Как назначать людей: по имени или по компетенции

Потребность по компетенции (`skill_id`) даёт решателю свободу выбрать человека. Если каждый человек входит ровно в одну востребованную компетенцию и нигде не назначен по имени, пул точен: соблюдена ёмкость пула — значит, людей можно расставить поимённо. Иначе после расчёта каждая потребность привязывается к конкретному человеку; если привязка без конфликтов невозможна, план пересчитывается с выбранными людьми. В отчёте это видно по `metadata.skill_binding`: `exact`, `pool` или `two_phase`.

## MS Project XML (MSPDI)

Импорт: `import файл1.xml файл2.xml --codes okr1 okr2`. Каждый файл — одна ОКР, идентификаторы работ получают префикс кода (`okr1.12`).

| Поле MS Project | Во что превращается |
|---|---|
| Суммарная задача | Узел структуры работ (уровень 1 — этап, глубже — пакет) |
| Обычная задача | Работа; длительность в рабочих днях по `MinutesPerDay` (меньше дня — округляется до 1 с отметкой) |
| Веха или нулевая длительность | Веха |
| `PredecessorLink` Type 0/1/2/3 | Связь FF/FS/SF/SS |
| `LinkLag` | Лаг в рабочих днях; процентный лаг — от длительности предшественника; календарный (elapsed) лаг — приближение ×5/7 с отметкой |
| Ограничение SNET | `earliest_start` |
| Ограничение FNLT | `latest_finish` |
| Ограничение MSO | `pinned` |
| Ограничение MFO | `latest_finish` и `earliest_start` |
| Ограничения ALAP, SNLT, FNET | Пропускаются с отметкой в отчёте импорта |
| `Deadline` | Директивный срок; с `--soft-deadlines` — плановый |
| Трудовой ресурс, `MaxUnits` | Человек (`1.0` = 10 единиц) или группа, если больше 1.0 |
| Материальный или затратный ресурс | Пропускается с отметкой |
| Назначение `Units` | Потребность работы в ресурсе (не больше `MaxUnits`, иначе урезается с отметкой) |
| `PercentComplete`, `ActualStart`, `ActualFinish`, `RemainingDuration` | Статус и остаток |
| `Start`, `Finish` | `planned_start`, `planned_finish` |
| Базовый план 0 | `baseline_start`, `baseline_finish` |

XML разбирается безопасным парсером (`defusedxml`): внешние сущности и «XML-бомбы» отклоняются.

## MS Project MPP и MPX

Импорт: `import okr1.mpp` (и `.mpx`). Файл читает библиотека MPXJ, поэтому нужны Java 17 и `pip install "SynAPS-ProgramPlan[mpp]"`. Суммарные задачи, работы, связи, трудовые ресурсы и ограничения переносятся по той же таблице, что и для XML выше. Базовый план из MPP не переносится. Всё пропущенное — в `notes` отчёта импорта.

Экспорт: `export program.json plan.json --out plan.xml` записывает только принятый план: ОКР → пакет → работа, связи с лагами, трудовые ресурсы и назначения, директивный срок в `Deadline`, хеш плана и текст объяснения в `Notes`. Работы стоят в ручном режиме с проверенными датами. Базовый план 0 — даты, с которыми сравнивался принятый план (`Baseline`). В заголовок файла пишутся начало и конец горизонта программы (`StartDate`, `FinishDate`) и дата статуса (`StatusDate`). Обратный импорт этого файла снова проходит проверку: дата статуса лежит внутри горизонта. Закрепления и ограничения «не раньше / не позже» в файл не переносятся.

Потери импорта — список `losses`: у каждой записи код, объект, действие (`skipped`, `approximated`, `clamped` или `info`) и тот же текст, что в `notes`. `import --losses losses.json` пишет этот список. `import --strict` не создаёт программу и возвращает код 2, если есть пропуск, приближение или урезание. Записи `info` (базовый план Primavera в этом файле отсутствует, сработавшее соответствие имён) импорт не останавливают.

Таблица соответствий ресурсов: `import a.xml b.xml --aliases names.csv`. Колонки `alias` и `canonical` (допускаются `from` и `to`). Одинаковое каноническое имя становится одним общим ресурсом, даже если в файлах написано по-разному. Похожие имена, которых в таблице нет, в отчёт попадают и сами не сливаются.

## Primavera P6 XER

Импорт: `import portfolio.xer`. Файл XER — текстовая выгрузка таблиц Primavera (`%T` — таблица, `%F` — поля, `%R` — строки); кодировка UTF-8, при ошибке — Windows-1251. Один файл может содержать несколько проектов: каждый проект становится ОКР с кодом из `proj_short_name`, идентификаторы работ — `код.task_code`.

| Таблица и поле Primavera | Во что превращается |
|---|---|
| `PROJECT` | ОКР; `last_recalc_date` или `next_data_date` — дата статуса |
| `PROJWBS` | Узлы структуры работ; корневой узел проекта отбрасывается, первый уровень — этап, глубже — пакет |
| `TASK` типа `TT_Task`, `TT_Rsrc` | Работа; длительность `target_drtn_hr_cnt` делится на часы рабочего дня календаря работы (`CALENDAR.day_hr_cnt`, по умолчанию 8) |
| `TASK` типа `TT_Mile`, `TT_FinMile` | Веха |
| `TASK` типа `TT_LOE`, `TT_WBS` | Пропускается с отметкой: у работ уровня усилий и суммарных нет своей длительности |
| `status_code` `TK_Complete` | Выполненная работа (нужны фактические даты, иначе остаётся плановой с отметкой) |
| `status_code` `TK_Active` | Выполняемая работа с остатком `remain_drtn_hr_cnt` |
| `early_start_date`, `early_end_date` (или `target_*`) | `planned_start`, `planned_finish` |
| Ограничение `CS_MSOA` (начало не раньше) | `earliest_start` |
| `CS_MEOB` (окончание не позже), `CS_MEO`, `CS_MANDFIN` | `latest_finish` |
| `CS_MSO`, `CS_MANDSTART` | `pinned` |
| `CS_MSOB`, `CS_MEOA`, `CS_ALAP` | Пропускаются с отметкой |
| `TASKPRED` `PR_FS`, `PR_SS`, `PR_FF`, `PR_SF`, `lag_hr_cnt` | Связь с лагом в рабочих днях по календарю предшественника; связь между проектами — межпроектная |
| `RSRC` `RT_Labor` | Человек или группа |
| `RSRC` `RT_Equip` | Оборудование (стенд) |
| `RSRC` `RT_Mat` | Пропускается с отметкой |
| `RSRCRATE.max_qty_per_hr` | Ёмкость ресурса (`1.0` — одна полная единица) |
| `TASKRSRC.target_qty_per_hr` | Потребность работы в ресурсе |

Базовый план Primavera хранится отдельным проектом и не импортируется: эталон для сдвигов — даты текущего плана. Об этом пишет отчёт импорта.

|---|---|

| `src_uid` | UID работы в MS Project |
| `dst_project` | Код ОКР последователя |
| `dst_uid` | UID работы-последователя |

## Сценарии «что если»

Файл JSON — список сценариев; каждый становится вариантом E1, E2, …:

```json
[
  {"label": "второй стенд ТС-1", "add_capacity": {"stand-1": 1}},
  {"label": "веха ОКР-2 на месяц позже", "move_deadline": {"okr2.ms3": "2028-03-31"}},
  {"label": "без ОКР-4", "drop_projects": ["okr4"]},
  {"label": "испытания дольше на 15 дней", "delay_task_wd": {"okr1.t17": 15}}
]
```

| Поле | Действие |
|---|---|
| `add_capacity` | Добавить ёмкость ресурсу (в его единицах) |
| `move_deadline` | Новый директивный срок работы или вехи (снимает `latest_finish`) |
| `drop_projects` | Исключить ОКР из программы вместе с её связями |
| `delay_task_wd` | Удлинить ещё не начатую работу на N рабочих дней |

## Файл программы (`program.json`)

Полное описание одного расчёта, схема `SynAPS-ProgramPlan.program.v1`. Поле `schema_version` можно не писать: так сохранены файлы до появления поля, и они читаются как эта версия. Любая другая строка в поле — отказ с кодом 2. Хеш входа считается по каноническому JSON, поэтому порядок ключей в файле его не меняет. Команда `diff before.json after.json` показывает, какие работы, связи, ресурсы, проекты и даты разошлись. Состав файла: `program`, `calendars`, `projects`, `wbs`, `tasks`, `dependencies`, `resources`, `skills`, `capacity_exceptions`, `baseline`, `freeze`, `risk_drivers`, `provenance`. Поля задач, ресурсов и драйверов риска — те же, что в Excel. Дополнительно в JSON доступны:

- `calendars[].base`: `RU_PRODUCTION`, `FIVE_DAY`, `SEVEN_DAY`, плюс `extra_holidays` и `extra_workdays`;
- `baseline.task_dates`: утверждённые даты работ;
- `freeze.freeze_until`: работы, утверждённое начало которых раньше этой даты, не двигаются;
- `provenance.kind`: `synthetic`, `open_data`, `customer_anonymized`, `experiment`, а также `source` и `source_file_hash`.

Модель строгая и отклоняет с понятной ошибкой (код выхода 2): неизвестное поле, повтор идентификатора, ссылку на несуществующую ОКР, работу, ресурс или компетенцию, отрицательную длительность, веху с ресурсами, потребность больше ёмкости ресурса, выполненную работу без фактических дат, цикл жёстких связей и максимальные лаги, которые противоречат друг другу.

## Файл плана (`plan_*.json`)

Схема `SynAPS-ProgramPlan.result.v1`.

| Раздел | Содержание |
|---|---|
| `scenario_id`, `label` | Вариант (`A`, `B`, …, `E1`, `R1`, `repair`) и его название |
| `outcome` | `ok`, вердикт `claim`, статус решателя, `kernel_verified`, число жёстких нарушений, `detail` |
| `tasks[]` | Для каждой работы: начало, окончание, длительность, статус, назначенные люди (`bound`), утверждённые даты, сдвиг `shift_wd`, признак критичности, резерв |
| `kpi` | Окончание программы и каждой ОКР, вехи и их опоздание, просрочка, сдвиги, пиковая и средняя загрузка ресурсов |
| `violations[]` | Нарушения (`hard`), отклонения показателей (`kpi`), предупреждения (`warning`) |
| `explanations[]` | Причина `cause_code`, участники, цепочка, текст, контрфакт и факт `fact`: тип, ресурс, ОКР, блокер, даты, хеш плана и хеш входа |
| `evidence` | Доказательная база: название и версия, коммит ядра, уровень утверждений, происхождение данных, хеш входа, настройки и их хеш, среда выполнения, `plan_hash` |
| `metadata` | Служебные сведения расчёта: способ привязки людей, сценарий «что если», а у варианта с правками — `replan`: исходный вариант, закреплённые работы, режим (`stable` или `optimise`) и, если был переход к переоптимизации, вердикт неудавшейся попытки (`stable_claim`) |

## Файл правок (`edits_*.json`)

Сохраняется кнопкой «скачать правки (JSON)» и читается командами `check --moves` и `replan --moves`:

```json
{
  "scenario": "A",
  "plan_hash": "cc3b4db063dd…",
  "moves": {"okr1.TP.1": "2027-03-10", "okr2.PI.M": "2027-11-15"}
}
```

`moves` — новая дата начала работы (для вехи — дата вехи). Если дата приходится на выходной или праздник, работа начнётся в следующий рабочий день, а веха встанет на конец предыдущего рабочего дня: веха — событие в конце дня. Допускается и плоский объект `{"работа": "дата"}`. `plan_hash` показывает, к какому варианту относились правки; работы, которых нет в плане, отклоняются с кодом выхода 2. Начатые и выполненные работы двигать нельзя.

## Результат оценки риска (`risk.json`)

| Поле | Содержание |
|---|---|
| `scenario_id`, `plan_hash` | По какому принятому плану считано |
| `runs`, `seed`, `scheduled_runs` | Число выборок, seed, сколько выборок поместилось в горизонт |
| `program_finish` | `p50`, `p80`, `p90` окончания программы |
| `deadlines_met_share` | Доля выборок, в которых соблюдены все директивные сроки (`null`, если сроков нет) |
| `milestone_risk[]` | По каждой вехе: `p50`, `p80`, `p90`, `target` (срок), `hard` (директивный ли), `on_time_share` (доля выборок в срок), `samples` |
| `drivers[]` | По каждому драйверу: `probability`, `occurred_share` (доля выборок, где риск случился), `p80_without` (P80 без этого риска), `p80_gain_wd` (на сколько рабочих дней раньше стал бы P80), `tasks` |
| `criticality` | Индекс критичности каждой работы (без `--brief`) |
| `unbound_tasks` | Работы, у которых потребность по компетенции не привязана к человеку: в выборке они идут без этого ресурса |
| `note` | Как понимать результат и сколько выборок отброшено |

## Журнал решений (`decisions.jsonl`)

Текстовый файл, одна запись JSON на строку, только дописывается.

| Поле | Содержание |
|---|---|
| `seq` | Номер записи, с 1 подряд |
| `at` | Время UTC в формате ISO 8601 |
| `user`, `role` | Кто и в какой роли (`planner`, `manager`, `observer`) |
| `action` | `accept` — принят, `reject` — отклонён, `repair` — пересчёт с правками |
| `scenario_id` | Вариант |
| `plan_hash` | Хеш плана, о котором решение (для неудавшегося пересчёта — `null`) |
| `input_hash` | Хеш входной программы |
| `reason` | Обоснование |
| `details` | Подробности: вердикт, а для пересчёта — исходный вариант, правки, запрошенный и фактический режим |
| `prev` | Хеш предыдущей записи (у первой — 64 нуля) |
| `hash` | SHA-256 канонического JSON записи без поля `hash` |

Проверка цепочки — `SynAPS-ProgramPlan journal decisions.jsonl`. Варианты с правками сохраняются рядом как `plan_R1.json`, `plan_R2.json`, … и при перезапуске рабочего места подгружаются, только если их хеш совпадает с журналом.
