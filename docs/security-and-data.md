# Данные и безопасность

Правила закрытого контура и меры, которые уже стоят в коде SynAPS-ProgramPlan.

## 1. Правила обращения с данными

1. **Только обезличенные данные.** Фамилии, названия изделий, шифры тем и организаций заменяются кодами до передачи в систему. Скрипт `scripts/anonymize_program.py` заказчик запускает у себя: имена и коды становятся последовательными кодами `C0001`, каждая дата сдвигается на одно и то же число дней, длительности, связи и ёмкости остаются. Соответствие кодов исходным именам скрипт не записывает. Результат в git не кладётся.
2. **Только в закрытом контуре.** Расчёт выполняется локально: командная строка, рабочее место и HTTP-контур не обращаются во внешнюю сеть, отчёт открывается без интернета (без внешних скриптов, шрифтов и CDN).
3. **Не в git.** Данные заказчика никогда не попадают в репозиторий. `.gitignore` исключает рабочие каталоги (`out/`), а демонстрация и тесты работают только на учебных данных.
4. **Происхождение обязательно.** У каждой программы есть поле `provenance`: `synthetic`, `open_data`, `customer_anonymized` или `experiment`, источник и хеш исходного файла. Происхождение переходит в доказательную базу каждого плана и показывается на первом экране отчёта.

## 2. Правила для искусственного интеллекта

- Языковая модель **не создаёт ограничения** и **не меняет план** без проверки.
- Объяснения строятся **только из структурированных фактов** итогового проверенного плана: активное ограничение, связь, занятый ресурс, календарь.
- Модель может только переформулировать уже вычисленные факты; в версии 0.1.0 языковая модель не используется вовсе.
- Ни один план не попадает в отчёт, экспорт, рабочее место или HTTP-ответ 200 без `outcome.ok`; ручная правка проверяется той же независимой проверкой.

## 3. Что обеспечено в коде

| Мера | Как реализовано |
|---|---|
| Безопасный разбор XML | MS Project XML читается через `defusedxml`: внешние сущности, DTD-атаки и «XML-бомбы» отклоняются |
| Книга Excel | Перед чтением архив проверяется: не больше 64 частей, 32 МиБ в распакованном виде и сжатие не сильнее чем в 100 раз |
| Размер программы | Не больше 100 000 работ, 400 000 связей, 20 000 ресурсов, 100 000 исключений календаря, 10 000 драйверов риска и горизонта в 8 000 дней. Меньший потолок задают `SYNAPS_PROGRAMPLAN_MAX_TASKS`, `MAX_LINKS`, `MAX_RESOURCES`, `MAX_EXCLUSIONS`, `MAX_RISK_DRIVERS`, `MAX_HORIZON_DAYS`. Горизонт раньше 2000-01-03 не принимается |
| Память решателя | При `SYNAPS_PROGRAMPLAN_MEMORY_MB` расчёт HTTP идёт в отдельном процессе и останавливается, когда рабочий набор превышает потолок |
| Строгая проверка входа | Модель Pydantic в строгом режиме: неизвестные поля, неверные типы и висячие ссылки отклоняются с кодом выхода 2 или HTTP 422 |
| Отказ по умолчанию | Непринятый план не отдаётся: HTTP 409, код выхода 1, экспорт и риск отказываются работать |
| Отсутствие хранения | Вычислительный HTTP-контур не хранит программы и планы; рабочее место хранит только журнал решений и варианты с правками в указанном каталоге |
| Автономный отчёт | HTML без внешних ресурсов, все данные встроены в файл. В блоке JSON символы `<`, `>` и `&` записаны как экранирование Юникода, поэтому имя из импорта не закрывает этот блок. CSP запрещает загрузку извне и отправку форм. Собственный сценарий страницы остаётся встроенным: иначе файл отчёта не открывается без сервера. Это остаточный риск встроенного сценария, не дыра в данных |
| Целостность | Хеш входной программы, настроек и плана в доказательной базе; ядро зафиксировано полным коммитом; журнал решений связан хеш-цепочкой |
| Без выполнения внешнего кода | Импорт не выполняет макросы и формулы: книга Excel читается в режиме значений |
| Разграничение прав | Рабочее место: роли планировщика, руководителя и наблюдателя, проверка права на каждом запросе, отказ по умолчанию (401/403) |
| Заголовки ответа | `Content-Security-Policy` (`default-src 'none'`, запросы только к своему серверу, запрет встраивания в чужие страницы), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` |

## 4. Роли и доступ к рабочему месту

**Локальный режим** — без настройки. Один пользователь `local` с ролью планировщика. Сервер принимает запросы только с заголовком `Host` локального адреса (`127.0.0.1`, `localhost`, `::1`): так браузер на той же машине не может быть использован чужой страницей через подмену DNS (DNS rebinding). Запуск `serve` на другом адресе без ролей отклоняется с кодом выхода 2.

**Режим с ролями.** Администратор задаёт до запуска переменную окружения:

```text
SYNAPS_PROGRAMPLAN_TOKENS=<токен>=planner:ivanov,<токен>=manager:petrova,sha256:<хеш токена>=observer:sidorov
```

- Каждый элемент — `токен=роль:пользователь`; роли — `planner`, `manager`, `observer` (права — в [руководстве](user-guide.md#11-рабочее-место-планировщика)).
- Вместо самого токена можно указать `sha256:` и его хеш SHA-256 в шестнадцатеричном виде: тогда секрет не хранится даже в окружении сервера. Сравнение выполняется по хешу за постоянное время.
- Токен передаётся в заголовке `Authorization: Bearer`; браузер хранит его в памяти вкладки (`sessionStorage`) до её закрытия. Куки не используются, поэтому подделка межсайтовых запросов (CSRF) неприменима.
- Токены должны быть длинными и случайными (не меньше 32 случайных байт, например `python -c "import secrets; print(secrets.token_urlsafe(32))"`): ограничения числа попыток в рабочем месте нет.
- Пользователь и роль из токена попадают в каждую запись журнала.

**Сеть.** Локальный адрес слушается по HTTP. Любой другой адрес `serve` принимает только с `--tls-cert` и `--tls-key` и только при включённых ролях; иначе запуск завершается с кодом 2. Обычная схема контура: процесс на `127.0.0.1`, перед ним обратный прокси с TLS.

**Корпоративный вход.** Сервер не подключается к каталогу сам. Прокси, который уже выполнил вход (OpenID Connect, Kerberos, LDAP), передаёт личность заголовками `X-Remote-User` и `X-Remote-Role` (`planner`, `manager` или `observer`) вместе с секретом `X-Synaps-Proxy-Secret`. Секрет задаётся переменной `SYNAPS_PROGRAMPLAN_PROXY_SECRET` и сравнивается за постоянное время. Заголовок пользователя без верного секрета игнорируется; неверный секрет — отказ 401, а не локальный режим.

## 5. Журнал решений

Журнал (`decisions.jsonl`) только дописывается. Каждая запись содержит хеш SHA-256 предыдущей и свой хеш. Если задан ключ `SYNAPS_PROGRAMPLAN_JOURNAL_KEY` (или `journal --key`), к записи добавляется подпись HMAC-SHA256 этого хеша. Проверка с тем же ключом не принимает запись без подписи и запись с чужой подписью. Без ключа подпись не сверяется, и журнал, начатый до включения ключа, по-прежнему проходит проверку цепочки. Команда `journal` и рабочее место обнаруживают:

- изменение любой записи;
- удаление или перестановку записи внутри журнала;
- нарушение нумерации.

Рядом пишется печать `decisions.jsonl.head`: число записей и хеш последней, замена файла атомарная. Поэтому обнаруживается и то, чего одной цепочки мало:

- удаление последних записей, после которого оставшаяся цепочка всё ещё сходится;
- замена журнала новым файлом с собственной цепочкой.

Печать не прячет порчу: `journal --seal` записывает её только если печати ещё нет или она совпадает с файлом. Рабочее место с испорченным журналом или печатью не запускается.

Чего пара «журнал + печать» **не** обнаруживает: одновременную подмену обоих файлов. Для этого хеш последней записи (`head` в ответе `journal`) фиксируется вне системы — в протоколе совещания или отдельном хранилище — и проверяется `journal --anchor`. Права на запись обоих файлов — только у учётной записи сервера; файлы входят в резервное копирование. Варианты с правками (`plan_R*.json`) после перезапуска подгружаются, только если их пересчитанный хеш совпадает с журналом и независимая проверка чиста, поэтому подменённый файл плана не попадёт в интерфейс.

## 6. Контур заказчика

- **Сеть.** Вычислительный HTTP — отдельный процесс: рабочее место его не загружает. Локальный клиент (`127.0.0.1`, `localhost`, `::1`) обслуживается по HTTP. Чужой адрес получает ответ только по HTTPS: токен по открытому HTTP не принимается. Перед процессом на локальном адресе стоит прокси, который завершает TLS. Без токенов чужой адрес получает 401; с токенами каждый запрос требует `Authorization: Bearer`. Переменная `SYNAPS_PROGRAMPLAN_RATE_PER_MIN` ограничивает число запросов с одного адреса за минуту; сверх лимита ответ 429. Если переменная не задана, частоту держит прокси контура. Рабочее место вне локального адреса запускается с ролями и TLS. Корпоративный вход — прокси с секретом `SYNAPS_PROGRAMPLAN_PROXY_SECRET`. Ошибка модели и дата вне календаря на `/solve` — 422, а не внутренний сбой.
- **Доступ к файлам.** Каталоги с программами, планами и журналом защищаются средствами ОС. Отчёт HTML содержит данные программы и хранится вместе с ней.
- **Установка.** Версии зафиксированы. `python scripts/fetch_wheelhouse.py` на машине с сетью скачивает колёса в `wheelhouse` и пишет `requirements-hashed.txt` с хешами SHA-256. Каталог колёс в git не входит. Перечень компонентов — `sbom.cdx.json`. Точки входа и пределы собраны в [модели угроз](threat-model.md).
- **Токены.** Выдача, хранение и отзыв — процедура администратора. Отзыв — удалить строку и перезапустить процесс. Срок токена и ограничение попыток ставит прокси перед локальным адресом.

## 7. Поставка

Лицензия MIT. Перечень компонентов — `sbom.cdx.json`. Журнал с хеш-цепочкой и печатью, роли, CSP, безопасный разбор XML. Рабочее место ведёт одну программу: пересчёты идут по очереди, каждая правка проходит ту же независимую проверку. В одном запросе рабочего места — до 5000 правок.
