# Качество и доказательность

Как убедиться, что плану SynAPS-ProgramPlan можно доверять, и как это проверить самостоятельно. Короткий ответ: каждый план дважды проверяется независимыми средствами, каждое утверждение о системе записано в реестре и закрыто тестом, а каждый план несёт доказательную базу, по которой расчёт можно повторить.

## 1. Три уровня защиты от неверного плана

| Уровень | Что делает | Где |
|---|---|---|
| Строгая модель данных | Не пропускает неизвестные поля, висячие ссылки, циклы связей, противоречивые лаги, вехи с ресурсами, выполненные работы без фактических дат | `model.py` |
| Проверка ядра SynAPS | Проверяет итоговые назначения на допустимость в терминах ядра | ядро SynAPS |
| Независимая доменная проверка | Заново проверяет календарь, сроки, связи, загрузку, закрепления, пулы — по исходной программе, без решателя | `checker.py` |

План, не прошедший любой уровень, не публикуется. Тест `test_checker_stays_independent_of_the_solver_path` следит, чтобы доменная проверка не начала зависеть от компилятора, планировщика или решателя.

## 2. Что проверяют автоматические тесты

Набор `tests/` (196 тестов) запускается командой `python -m pytest tests -q` и в CI при каждом изменении. Замер 2026-10-07 на Windows, Python 3.12: 196 тестов, 11 с внутри pytest. Число записано в `evidence.json`. Команда `python scripts/build_evidence.py --check` сверяет его с README, английским README, этим разделом, реестром разрывов и планом пилота и с фактически собранными тестами. Расхождение или пропуск теста роняют прогон. Цифры показа в README и в сценарии показа сверяются с тем же файлом. CI показ заново не считает: лимит 8 секунд на другой машине может дать другой допустимый план.

| Область | Что доказывают тесты |
|---|---|
| Календарь | 2025, 2026, 2027 годы — по 247 рабочих дней по постановлениям; праздники и переносы; годы без постановления помечены как предварительные; ось рабочих дней обратима |
| Модель | Вехи без ресурсов; потребность — ровно в одном ресурсе или компетенции; висячие ссылки, циклы и противоречивые максимальные лаги отклоняются; приоритет утверждённых дат |
| Планировщик | Веха в день окончания предшественника; цепочки FS; общий стенд разводит две ОКР; связи SS, FF, FS с опережением, SF; максимальный лаг; выполненные и выполняемые работы; закрепление; отпуск; пул компетенции; жадный план одной длительности проверяется так же; на программе с режимами жадный диспетчер не строит план; стабильность не двигает работы раньше утверждённого; недоказанная невыполнимость не выдаётся за доказанную; одинаковое начальное число генератора — одинаковый хеш плана |
| Независимая проверка | Принятый план чист; каждое нарушение ловится своим кодом; перегрузки ресурса и пула; пропавшие и лишние работы; **150 случайных сдвигов принятого плана — ни одного ложного принятия** |
| Режимы и переналадка | CP-SAT оставляет ровно один режим; жадный диспетчер отвечает `UNSUPPORTED_MODEL` и дат не отдаёт; чужой режим и чужие ресурсы отклоняются; между разными состояниями стенда остаётся интервал из матрицы; короткий интервал и наложение на работу ловятся; режимы и переналадка одной работы вместе отклоняются; программа без этих полей не меняет хеш |
| Конфликты | Конкуренция двух ОКР за стенд и нарушенная связь в исходных планах |
| Импорт и экспорт | MS Project XML: импорт, слияние, общий ресурс, круговой обмен; Primavera XER: несколько проектов, межпроектные связи, лаги в часах, статусы, ограничения, работы уровня усилий; Excel: круговой обмен, пустые необязательные колонки, шаблон без данных, реестр рисков; PSPLIB: чтение задачи и таблицы оптимумов |
| Риск | Без разброса квантиль равен цепочке; без разброса и драйверов выборка воспроизводит принятый план день в день; связь с максимальным лагом сохраняет свой минимальный лаг; одинаковое начальное число генератора — одинаковые квантили; непринятый план не берётся базой; драйвер с высокой вероятностью ранжируется выше; драйвер, который не случается, не даёт выигрыша; ранние даты ограничивают выборку; исключение ОКР убирает её работы из драйверов |
| Правки | Привязка к рабочим дням; правка раньше предшественника и правка вехи за срок ловятся кодами независимой проверки; безвредная правка чиста; неизвестная работа и непринятый план отклоняются; пересчёт держит правку на месте; минимум перестановок не ставит ни одну работу раньше исходного варианта и не трогает независимые работы; переход к переоптимизации записывается; начатую работу двигать нельзя |
| Рабочее место | Отчёт и проверка в локальном режиме; чужой заголовок `Host` — отказ; пересчёт добавляет вариант и пишет журнал; невыполнимый пересчёт не публикуется; роли: 401 без токена, 403 без права, решения пишутся от имени пользователя; после перезапуска варианты восстанавливаются, нумерация продолжается, подменённый файл плана отбрасывается |
| Журнал | Изменение записи обнаруживается с номером записи; чистая цепочка проходит проверку; команда `journal` даёт код выхода 1 на испорченной цепочке; печать ловит обрезку хвоста и замену файла; одновременная подмена журнала и печати ловится внешним якорем |
| HTTP и командная строка | `/solve` с невозможным сроком — 409 и `accepted: false`; `/check` с нарушением — 409, без нарушения — 200; экспорт только принятого плана; цель `stability`; `check --moves` и `replan`; отчёт с разделом риска; `serve` без ролей или без TLS на внешнем адресе — отказ |
| Фиксация ядра | Во всех опубликованных файлах указан один и тот же коммит SynAPS, причём полным SHA, а не именем ветки |

Кроме тестов, CI выполняет `scripts/build_evidence.py --check` (цифры документов и закрепление Actions по SHA коммита), `ruff` (стиль и типичные ошибки), `mypy --strict` (типы) и `scripts/lint_claims.py` (запрещённые утверждения). Интерфейс рабочего места дополнительно проверен в браузере: перетаскивание, клавиатура, отмена, проверка на сервере, пересчёт, решение и журнал (см. [`AUDIT.md`](../AUDIT.md)).

## 3. Академический набор PSPLIB j30

PSPLIB (Kolisch, Sprecher, 1997) — стандартная библиотека задач календарного планирования с ограниченными ресурсами. Набор j30 — 480 задач по 30 работ с четырьмя возобновляемыми ресурсами; для всех известны оптимальные длительности. Каждая задача переводится в программу и проходит **тот же** путь, что программа заказчика: подготовка модели, CP-SAT, проверка ядра, независимая проверка.

| Показатель | Результат |
|---|---|
| Задач | 480 |
| Принято двойной проверкой | 480 (100%) |
| Длительность равна известному оптимуму | 476 (99,2%) |
| Вердикт `OPTIMAL` | 472; у всех длительность совпала с известным оптимумом — ложных доказательств нет |
| `FEASIBLE`, оптимум найден, но не доказан за 10 с | 4: j3013_5, j3029_3, j3029_6, j3045_6 |
| `FEASIBLE`, на одну единицу хуже оптимума | 4: j3013_1 (59 против 58), j3013_2 (63 против 62), j3013_6 (65 против 64), j3029_8 (81 против 80) |
| Среднее отклонение от оптимума | 0,013%; максимум 1,72% |
| Среднее отклонение от нижней оценки по критическому пути | 13,39% |
| Время | в среднем 0,21 с, максимум 6,6 с при лимите 10 с; один поток, начальное число генератора (`seed`) 42 |

Источники: задачи — зеркало PSPLIB в репозитории [ScheduleOpt/optalcp-benchmarks](https://github.com/ScheduleOpt/optalcp-benchmarks) (`benchmarks/rcpsp/data/j30`), оптимумы — таблица лучших известных решений Ghent University (`J30_BKS.csv`, [solutionsupdate.ugent.be](http://solutionsupdate.ugent.be/)). Файлы PSPLIB в репозиторий не входят. Повторить:

```text
python scripts/bench_psplib.py путь/к/j30 --opt J30_BKS.csv --time-limit 10 --seed 42 --out benchmarks/psplib_j30.json
```

На признанном эталоне решатель и двойная проверка отвечают за доли секунды, а каждый вердикт `OPTIMAL` совпадает с известным оптимумом.

### PSPLIB j60

Набор j60 — тоже 480 задач, но по 60 работ. Лимит решателя 10 с, `seed` 42: все 480 планов приняты двойной проверкой, 405 с вердиктом `OPTIMAL`, 75 допустимы, неотвеченных нет. Среднее отклонение от нижней оценки по критическому пути 11,62 %. Время от старта до ответа — в среднем 2,05 с, максимум 17,63 с (в него входит компиляция и проверка). Результат — `benchmarks/psplib_j60.json`. В отчёте прогона — принятие, доказанные оптимумы и отклонение от критического пути.

### PSPLIB j120

Самый крупный набор PSPLIB: 600 задач по 120 работ. Лимит решателя 10 с, `seed` 42: все 600 планов приняты двойной проверкой, у 259 оптимальность доказана, 341 допустимы, неотвеченных и ложных вердиктов нет. Среднее отклонение от нижней оценки по критическому пути 36,84 %: в j120 ресурсы загружены плотнее, и критический путь без ресурсов сильно занижает достижимую длительность. Время от старта до ответа — в среднем 7,43 с, максимум 20,23 с вместе с подготовкой модели и проверкой. Результат — `benchmarks/psplib_j120.json`.

### RCPSP/max (обобщённые связи и максимальные лаги)

Наборы j10, j20 и j30 библиотеки ProGen/max: 810 задач, у части из них расписания не существует. Связи — лаги «начало–начало», в том числе отрицательные, то есть и минимальная, и максимальная задержка. Эталон — таблица `optimum.csv` репозитория ptal/kobe-scheduling: точное значение, диапазон `нижняя..верхняя` или `unsat`. Лимит 10 с, `seed` 42, тот же путь проверки. Прогон считается проваленным, если принят план заведомо невыполнимой задачи, если длительность ниже опубликованной нижней оценки или если вердикт `OPTIMAL` не совпал с известным единственным оптимумом. Таких случаев нет.

| Набор | Задач | Допустимые найдены | Невыполнимость доказана | Совпало с известным оптимумом | Среднее время |
|---|---|---|---|---|---|
| j10 | 270 | 187 из 187 | 83 из 83 | 187 из 187 | 0,02 с |
| j20 | 270 | 184 из 184 | 86 из 86 | 158 из 158 | 0,16 с |
| j30 | 270 | 185 из 185 | 85 из 85 | 120 из 121 | 0,48 с |

На j30 одна задача с известным оптимумом не доказана и чуть хуже: PSP73, допустимый план 55 при оптимуме 53 (лимит 10 с). Ещё три допустимых плана чуть длиннее записанной верхней оценки диапазона: PSP151 (158 против 157), PSP153 (178 против 176), PSP154 (135 против 134); вердикт у них `FEASIBLE`, не `OPTIMAL`. Там, где эталон — диапазон, а не оптимум, часть доказанных планов короче записанной верхней оценки: для j20 это проверено на исходных лагах и ресурсах задач PSP71, PSP72 и PSP167, расписание исходной задачи не нарушено. Максимум одного прогона — 8,6 с.

Повторить: `python scripts/bench_psplib.py путь/к/j30 --ref optimum.csv --time-limit 10 --seed 42`. Результаты — `benchmarks/rcpspmax_j10.json`, `rcpspmax_j20.json`, `rcpspmax_j30.json`.

### Учебные программы из сотен и тысяч работ

Генератор учебных программ (`seed` 42, шесть работ на этап, запас директивного срока 3): число людей и стендов растёт вместе с числом ОКР, чтобы загрузка оставалась сравнимой. Лимит CP-SAT — 60 с. Все шесть планов приняты обеими проверками.

| ОКР | Работ | Связей | Жадный план | CP-SAT, 60 с |
|---|---|---|---|---|
| 16 | 672 | 1 115 | 10,7 с, просрочка 1 043 р.д. | 73,7 с, просрочка 477 р.д. |
| 32 | 1 344 | 2 225 | 13,6 с, просрочка 4 940 р.д. | 79 с, просрочка 2 710 р.д. |
| 64 | 2 688 | 4 435 | 34 с, просрочка 7 997 р.д. | 157 с, просрочка 5 790 р.д. |

CP-SAT на каждом размере сократил суммарную просрочку жадного плана: на 54 %, 45 % и 28 %. Сроки в учебных программах заданы с запасом, состав ресурсов и связи задаёт генератор; на пилоте тот же замер повторяется на программе заказчика. Повторить: `python scripts/bench_scale.py --sizes 16,32,64 --time-limit 60 --seed 42`. Результат — `benchmarks/scale.json`.

### Первый допустимый план на больших программах

Тот же генератор, четыре работы на этап, `seed` 42. Считается только жадный план: это первый допустимый план, без доказательства оптимума. Люди и стенды снова растут вместе с числом ОКР. Жадный поиск ядра сам ограничен 120 с. Модель ядра принимает не больше 10 000 рабочих центров, и в этой сборке центр приходится на каждую цепочку.

| ОКР | Работы | Связи | Ресурсы | Итог | Время | Память |
|---|---|---|---|---|---|---|
| 167 | 5 010 | 7 730 | 553 | принят | 117,8 с | 1 221 МБ |
| 290 | 8 700 | 13 433 | 966 | принятого плана нет: поиск остановился на 120 с | 122,1 с | 270 МБ |
| 334 | 10 020 | 15 443 | 1 113 | модель не собрана: рабочих центров 10 020 при пределе 10 000 | 0,8 с | 286 МБ |

Дальше 10 020 работ прогон не продолжался: предел ядра уже достигнут, и программы на 20 тысяч работ в эту границу не входят. Отдельно проверен тесный состав ресурсов: 5 010 работ при двух людях на компетенцию и четырёх стендах жадный план не построил (50,8 с, 180 МБ). Повторить: `python scripts/bench_boundary.py --projects 167,290,334 --tasks-per-stage 4 --seed 42`. Результат — `benchmarks/scale_boundary.json`. Сравнения j60 и j120 с лучшими известными решениями здесь нет: таблицы оптимумов для этих наборов под рукой не было. В реестре остаются принятие планов и доказанные оптимумы.

## 4. Атакующая проверка

Проверено кодом, а не рассказом:

- случайные сдвиги работ принятого плана: доменная проверка не приняла ни одного расписания, которое отвергает ядро;
- невозможный директивный срок: вердикт `INFEASIBLE`; в Гант, экспорт и HTTP 200 он не попадает;
- урезанная модель (подъём окон, вторая фаза привязки людей) никогда не выдаёт `INFEASIBLE`;
- оценка риска отказывается работать по непринятому плану;
- ручная правка, нарушающая связь, срок или ёмкость, ловится независимой проверкой; пересчёт, который не прошёл проверку, не публикуется;
- запрос к рабочему месту без токена, с чужим токеном или с чужим заголовком `Host` отклоняется; роль без права получает 403;
- изменённая запись журнала обнаруживается с номером; подменённый файл варианта не подгружается после перезапуска;
- реестр запрещает формулировки о готовности, которой нет, и о «доказанной вероятности» квантилей.

Сценарии атакующей проверки и разбор возражений собраны в [`AUDIT.md`](../AUDIT.md).

## 5. Воспроизводимость

- **Детерминизм.** CP-SAT работает в одном потоке с постоянным начальным числом генератора и детерминированным временем. Одинаковые данные и настройки дают одинаковый `plan_hash` (тест `test_same_seed_same_plan_hash`).
- **Фиксация версий.** Ядро SynAPS — по полному коммиту, OR-Tools — по точной версии.
- **Доказательная база** (`evidence` в каждом плане): название и версия, коммит ядра, уровень утверждений, уровень зрелости, происхождение данных, хеш входной программы, настройки и их хеш, среда выполнения (Python, ОС, версии библиотек), хеш плана.

Чтобы повторить расчёт: взять `program.json` с тем же `input_hash`, установить ту же версию с тем же коммитом ядра, запустить с настройками из `evidence.config` и сравнить `plan_hash`.

## 6. Дисциплина утверждений

- Всё, что о системе можно утверждать, записано в [`CLAIMS_REGISTRY.md`](../CLAIMS_REGISTRY.md) вместе с тем, чего утверждение **не** означает.
- [`BANNED_CLAIMS.txt`](../BANNED_CLAIMS.txt) перечисляет формулировки вне реестра; `scripts/lint_claims.py` ищет их во всех документах и коде и останавливает CI при находке.
- [`LIMITS.md`](../LIMITS.md) — границы применимости; [`AUDIT.md`](../AUDIT.md) — что проверено, триаж находок, атакующая проверка и разбор возражений.

## 7. Как проверить самостоятельно

```text
pip install -e ".[dev,api]"
python -m pytest tests -q
python scripts/lint_claims.py
SynAPS-ProgramPlan demo --out-dir out/demo
SynAPS-ProgramPlan check out/demo/program.json out/demo/plan_A.json
SynAPS-ProgramPlan serve out/demo/program.json out/demo/plan_A.json --journal out/demo/decisions.jsonl
```

Команда `check` прогоняет независимую проверку по готовому плану. Попробуйте вручную сдвинуть дату любой работы в `plan_A.json` и повторить — проверка покажет нарушение с кодом из [справочника](reference-codes.md#нарушения-независимой-проверки). То же самое мышью — в рабочем месте: перетащите работу раньше её предшественника и посмотрите на результат проверки. Затем исправьте строку в `decisions.jsonl` и выполните `SynAPS-ProgramPlan journal out/demo/decisions.jsonl` — проверка цепочки укажет испорченную запись.
