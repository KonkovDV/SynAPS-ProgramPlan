# SynAPS-ProgramPlan

**Сводный план программы ОКР: несколько проектов, общие люди и стенды, связи и сроки — в одном проверяемом плане, с риском срыва, ручной правкой и объяснением каждого переноса.**

SynAPS-ProgramPlan собирает планы отдельных ОКР (MS Project, Primavera P6 или книга Excel) в одну программу, находит конфликты за общие ресурсы, строит согласованный план и несколько альтернатив, оценивает риск срыва сроков и показывает, почему каждая работа стоит там, где стоит. Планировщик может перетащить работу на диаграмме Ганта, сразу увидеть, что нарушено, пересчитать план с этой правкой и записать решение в журнал. Расчёт выполняет ядро [SynAPS](https://github.com/KonkovDV/SynAPS) (решатель Google OR-Tools CP-SAT), а каждый план — и оптимизированный, и исправленный вручную — проверяется второй, независимой проверкой.

> **Уровень зрелости 0.1.0 — эксперимент.** Стенд проверен на синтетических программах, академическом наборе PSPLIB и автоматических тестах: ISO 16290 TRL 4. Результатов на данных заказчика пока нет, оценка по ГОСТ Р 58048 не проводилась. Всё, что о системе можно утверждать, перечислено в [`CLAIMS_REGISTRY.md`](CLAIMS_REGISTRY.md); границы — в [`LIMITS.md`](LIMITS.md).

## Что получает руководитель программы

| Требование заказчика | Что делает SynAPS-ProgramPlan | Чего пока нет |
|---|---|---|
| **F1. Сводный план** программы из планов отдельных ОКР | Импорт нескольких файлов MS Project (XML, а также MPP и MPX через MPXJ — нужны Java 17 и пакет `mpxj`), Primavera P6 XER (несколько проектов в одном файле, межпроектные связи — из самого файла) или одной книги Excel; одноимённые ресурсы разных проектов распознаются как общие; межпроектные связи для MS Project — из таблицы CSV; отчёт импорта перечисляет всё, что приближено или пропущено | 1С; базовый план из XER; бинарный MPP проверен библиотекой MPXJ на XML и MPX, не на файле заказчика |
| **F2. Связи, вехи, сроки и лимиты** | Связи «окончание–начало», «начало–начало», «окончание–окончание», «начало–окончание» с задержкой и максимальной задержкой; вехи; директивные (жёсткие) и плановые (мягкие) сроки; лимит сдвига; закрепление; заморозка ближнего горизонта; отпуска и ремонты; российский производственный календарь | Прерывание работы на время отпуска или ремонта ресурса; несколько режимов выполнения |
| **F3. Конфликты и риск срыва** | До оптимизации: перегрузки, конкуренция ОКР за один ресурс, нарушенные связи, невозможные и рискованные сроки, качество исходных данных. После: P50/P80/P90 окончания программы и вех, доля выборок «в срок» по каждой вехе, индекс критичности, реестр **драйверов риска** (вероятность и влияние) с ранжированием по вкладу в P80 | Экспертная оценка на данных заказчика; корреляции между рисками |
| **F4. Несколько вариантов** и их влияние | Варианты A «Сроки», B «Резерв ресурсов», C «Стабильность», D «Баланс», P «Приоритет ОКР» (если приоритетов больше одного), E «Что если» (добавить стенд, перенести веху, исключить ОКР, удлинить работу) и R — «правка планировщика»; таблица сравнения; одинаковые варианты сводятся в один | Пакет вариантов из одного вызова ядра |
| **F5. Гант, загрузка, критические работы, отклонения, причины изменений** | HTML-отчёт без сети и **рабочее место планировщика** (`serve`): Гант с исходным планом, критическими работами, вехами и сроками; перетаскивание работ мышью или клавиатурой с мгновенной независимой проверкой; пересчёт плана с закреплёнными правками и минимумом перестановок; тепловая карта загрузки; причина и первопричина каждого переноса; принятие и отклонение варианта с обоснованием в журнале с хеш-цепочкой; роли; выгрузка в MS Project | База данных и одновременная правка несколькими пользователями; вход через корпоративный каталог |

Подробная карта «требование → код → тест → документ»: [`docs/traceability-matrix.md`](docs/traceability-matrix.md).

## Как принимается план

План попадает в отчёт, диаграмму Ганта, рабочее место и HTTP-ответ, только если выполнены **все три** условия:

1. решатель вернул допустимое решение;
2. проверка ядра SynAPS не нашла нарушений;
3. независимая доменная проверка (`checker.py`, не использует решатель) не нашла ни одного жёсткого нарушения: сроков, связей, загрузки, календаря, закреплений.

Ручная правка проверяется **той же** независимой проверкой: план, исправленный мышью, судится по тем же правилам, что и оптимизированный. Пересчитанный с правками вариант публикуется только при `outcome.ok`.

Итог каждого расчёта — один вердикт:

| Вердикт | Что это значит для руководителя |
|---|---|
| `OPTIMAL` | План принят. Решатель доказал, что лучше по заданной цели на этой модели нельзя. |
| `FEASIBLE` | План принят. Он выполним и проверен, но за отведённое время не доказано, что он лучший. |
| `HEURISTIC_FEASIBLE` | План принят. Построен быстрым эвристическим методом и проверен. |
| `INFEASIBLE` | Доказано: при этих сроках, связях и ресурсах программа невыполнима. Система показывает, какие требования несовместимы и насколько их нужно ослабить. |
| `REJECTED` | Решатель что-то вернул, но проверка нашла нарушение. Такой план не показывается. |
| `ERROR` | Плана нет, и невыполнимость не доказана (например, кончилось время). |

Подробнее о вердиктах и кодах нарушений — в [`docs/reference-codes.md`](docs/reference-codes.md).

## Быстрый старт

Нужен Python 3.12 или новее.

```text
pip install "SynAPS-ProgramPlan[api] @ git+https://github.com/KonkovDV/SynAPS-ProgramPlan.git"
SynAPS-ProgramPlan demo --out-dir out/demo
SynAPS-ProgramPlan serve out/demo/program.json out/demo/plan_A.json out/demo/plan_D.json --journal out/demo/decisions.jsonl --risk-runs 200
```

Команда `demo` за 1–3 минуты создаёт синтетическую программу из четырёх ОКР с общими стендами, людьми и реестром рисков, строит варианты A–E и пишет в `out/demo`:

- `report.html` — отчёт по принятым вариантам с разделом риска;
- `report_infeasible.html` — пример программы с невозможным сроком и объяснением, что именно несовместимо;
- `program.json`, `plan_*.json`, `risk_A.json` — исходные данные, планы с доказательной базой и оценка риска.

Команда `serve` открывает рабочее место планировщика на `http://127.0.0.1:8765/`: тот же отчёт, но с правкой, пересчётом, решениями и журналом.

## Рабочий цикл

| Шаг | Команда | Результат |
|---|---|---|
| 1. Получить шаблон | `SynAPS-ProgramPlan template --out program.xlsx` | Книга Excel с листами и колонками, включая реестр рисков |
| 2. Собрать программу | `SynAPS-ProgramPlan import okr1.xml okr2.xml --codes okr1 okr2 --links links.csv --out program.json` или `import portfolio.xer --out program.json` | Сводная программа, общие ресурсы, отчёт импорта |
| 3. Найти конфликты | `SynAPS-ProgramPlan analyze program.json` | Перегрузки, конкуренция, нарушенные связи, рискованные сроки, качество данных |
| 4. Построить варианты | `SynAPS-ProgramPlan scenarios program.json --out-dir out --explain` | Планы A–E и таблица сравнения |
| 5. Понять невыполнимость | `SynAPS-ProgramPlan witness program.json` | Несовместимые требования и нужные послабления |
| 6. Оценить риск | `SynAPS-ProgramPlan risk program.json out/plan_A.json --out risk.json` | P50/P80/P90, доля «в срок» по вехам, драйверы риска по вкладу в P80, критичность |
| 7. Собрать отчёт | `SynAPS-ProgramPlan report program.json out/plan_A.json out/plan_D.json --risk-runs 200 --out report.html` | HTML: сравнение, Гант, загрузка, риск, причины |
| 8. Работать с планом | `SynAPS-ProgramPlan serve program.json out/plan_A.json out/plan_D.json --journal decisions.jsonl` | Правка мышью, проверка, пересчёт, решения, журнал |
| 9. Проверить правки без сервера | `SynAPS-ProgramPlan check program.json out/plan_A.json --moves edits_A.json`, затем `replan … --moves edits_A.json --out plan_R1.json` | Нарушения правок; новый вариант с закреплёнными правками |
| 10. Вернуть в MS Project | `SynAPS-ProgramPlan export program.json out/plan_A.json --out plan_A.xml` | Принятый план в формате MS Project XML |
| 11. Перепланировать | `SynAPS-ProgramPlan repair program.json out/plan_A.json --status-date 2027-03-01 --freeze-wd 10 --out plan2.json --out-program program2.json` | Новый план от даты статуса с заморозкой ближайших 10 рабочих дней |
| 12. Проверить журнал | `SynAPS-ProgramPlan journal decisions.jsonl --tail 5` | Последние решения и целостность хеш-цепочки |

Пошаговое руководство с примерами: [`docs/user-guide.md`](docs/user-guide.md).

## Проверка на академическом наборе

Чтобы качество решателя можно было сравнить с мировыми результатами, контур прогнан на всех 480 задачах **PSPLIB j30** (классический набор задач календарного планирования с ограниченными ресурсами, Kolisch и Sprecher, 1997) с известными оптимумами:

| Показатель | Результат |
|---|---|
| Планов принято двойной проверкой | 480 из 480 |
| Найден известный оптимум | 476 из 480 |
| Доказан оптимум (`OPTIMAL`) | 472 из 480; у всех 472 длительность совпала с известным оптимумом |
| Среднее и максимальное отклонение от оптимума | 0,013% и 1,72% (одна единица времени на задаче j3013_1) |
| Среднее время | 0,21 с на задачу при лимите 10 с, один поток, seed 42 |

Это проверка решателя на однопроектных задачах из 30 работ, а не обещание качества на программах заказчика. Тот же контур прогнан на 810 задачах RCPSP/max (наборы j10, j20, j30: обобщённые связи и максимальные лаги, включая заведомо невыполнимые): все невыполнимые доказаны, все задачи с известным единственным оптимумом решены точно, кроме PSP73 набора j30 (допустимый план 55 при оптимуме 53). На синтетике план принят до 64 ОКР и 2 688 работ. Подробности и команды повтора — в [`docs/quality-assurance.md`](docs/quality-assurance.md#3-академический-набор-psplib-j30).

## Данные заказчика

Данные заказчика не хранятся в репозитории и не покидают закрытый контур. В работу принимаются только обезличенные данные, у каждой программы записано происхождение (`provenance`): синтетика, открытые данные, обезличенные данные заказчика или эксперимент. Отчёт показывает происхождение на первом экране. Рабочее место без настроенных ролей отвечает только на локальном адресе. Языковые модели не создают ограничения и не меняют план; объяснения строятся только из фактов проверенного плана. Подробнее: [`docs/security-and-data.md`](docs/security-and-data.md).

## Для разработчиков

```text
git clone https://github.com/KonkovDV/SynAPS-ProgramPlan.git
cd SynAPS-ProgramPlan
pip install -e ".[dev,api]"
python -m pytest tests -q
python scripts/lint_claims.py
ruff check src tests scripts
mypy src
```

SynAPS подключается напрямую, без форка, и фиксируется коммитом `786cf1b3bc915941558e7e50b2935de684a32643` в `src/synaps_programplan/versions.py`, `pyproject.toml`, `CLAIMS_REGISTRY.md` и этом файле; тест `tests/test_pin.py` следит, чтобы они совпадали. Обобщённые связи в ядре добавлены в [KonkovDV/SynAPS#45](https://github.com/KonkovDV/SynAPS/pull/45). Запуск из исходников: `python -m synaps_programplan`. Два HTTP-контура: рабочее место `SynAPS-ProgramPlan serve` (роли, журнал) и вычислительный сервис без хранения `uvicorn synaps_programplan.api:app` (только локально, без аутентификации). Бенчмарк PSPLIB: `python scripts/bench_psplib.py`.

Коды выхода команды: `0` — план принят или проверка чиста, `1` — принятого плана нет или найдено жёсткое нарушение, `2` — неверные входные данные.
